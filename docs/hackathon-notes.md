## 三、选题：日历 · 会议改期冲突

来源：https://octosense.org/cn/apps/calendar/ （官方 12 篇「应用体验指南」之一，官方明确说「按 OctoSense 应用指南选择场景」）

**场景**：会议改到更早的时间和另一间办公室，新的时段恰好与私人预约冲突。

**7 段结构 = 一份现成的设计简报**（可直接作为开发输入与答辩脚本）：

| 段 | 内容 | 对应交付物 |
| --- | --- | --- |
| 01 场景 | 会议改期撞上私人预约 | 一句话选题 |
| 02 步骤演示 | ①打开变更邀请 ②看见安排重叠 ③审阅改期提案 ④明确什么尚未确认 | 3 分钟演示脚本 |
| 03 应用内 | 日/周视图；对照新旧信息、查看来源、检查冲突；选择替代时段 | 主界面交互 |
| 04 App Card | 桌面卡片并列展示两项安排，给出可选时段，不必先打开整张日历 | 卡片层 |
| 05 上下文 | 邮件与消息（邀请来源）/ 天气与地图（路程与出发时间）/ 文档（会议资料） | 数据来源声明 |
| 06 授权边界 | 「发送改期建议」与「修改私人安排」是**两项独立授权**；改变已有承诺前先展示冲突 | 权限模型（Hub 预检必查） |
| 07 触发时机 | 邀请、日程变更、准备时刻分别触发；多次通知持续更新同一事件 | Agent 触发逻辑 |

**★ 官方在首课里给出的场景设计理念，正好点名了日历**：
> 「从被动查询到主动守护：**结合日历数据主动监控行程并提前预警**」

这就是评审想看的 Agentic 味道 —— 不是「你问它答」，而是它自己盯着状态变化、主动把冲突摆到你面前。答辩时这句话应当直接引用。

## 四、技术栈（官方首课纪要）

| 层 | 内容 |
| --- | --- |
| 系统 | OctoSense OS，多平台，底层 Rust |
| UI 渲染 | Makepad 引擎，GPU 渲染 |
| 应用逻辑 | **OctoScript** —— 为 AI 设计的流式脚本语言（`main.splash`） |
| 工作流 | **双环（OctoLoop）**：外环用强模型做规划与审查，内环用低成本模型写代码与执行；主 Agent 可克隆多个 Peer Agent 绑定不同模型 |
| 调试 | 结合工具 Agent 自动获取 UI 信息并做可视化调试 |
| 稳定性 | 开源项目高速迭代，比赛期间组织者会稳定环境 |
| 决赛 | **统一使用指定模型** |

**应用形态**：
- **进程应用** —— 完整应用
- **App Card** —— 动态卡片，可对话实时生成临时 UI，适合展示动态数据

> 日历场景的落地形态建议：主界面做「进程应用」，冲突处理与改期提案做「App Card」。

## 五、提交与评审（官网口径）

**硬性要求**
- 必须**可运行** —— 视频、设计稿不能代替可运行作品
- 必须 **Apache License 2.0** 开源在公开仓库，各轮评审以仓库为准
- 通过 Hub 检查 ≠ 验收通过；仍需在注明版本的环境中演示真实任务、授权与结果核验
- **no-facts 规则**：模型只写布局与数据绑定，事实由数据能力提供。邮件、消息、天气、工厂任务都要注明来源，**不得编造状态、操作成功或执行结果**

**评审权重**
1. 先看 **Agent 自动化能力**
2. 再看项目反哺与 OctoSense ROM 技术突破

**奖池**：¥50,000 —— 一等 1×¥20,000 / 二等 2×¥9,000 / 三等 3×¥4,000，含 MiniMax Token 额度。
