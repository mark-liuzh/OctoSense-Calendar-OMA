# OctoSense 日历 v0.5.6 需求可行性分析

> 日期：2026-10-12  
> 基线：v0.5.5（待 Ody 重签 manifest）  
> 目标：评估用户提出的「下一版本」功能清单是否能在 GOSIM Agentic App Hackathon 的约束内实现。

## 平台与比赛硬约束

- **应用形态**：单文件 Splash 脚本应用（`bundle/main.splash`），无独立后端、无数据库、无服务器。
- **宿主能力**：`storage`（本机私有存储，额度约 16 MiB）+ `net`（仅白名单域名）+ `model`（一次性模型调用，当前 `card-host` 真机不可用）+ `mail`（仅在完整 Shell 中读取会议邀请，不自动写入）。
- **网络白名单**：当前 `manifest.json` 仅声明 `api.open-meteo.com` 与 `geocoding-api.open-meteo.com`。
- **数据边界**：用户日程、待办、笔记**不出本机**；不读取系统日历、通讯录、邮件流；不做自动定位。
- **复赛版本冻结**：10/13 23:59，剩余时间不足 25 小时。

## 功能可行性判定

| 功能点 | 比赛/平台是否允许 | 本应用能否实现 | 关键限制 | 建议处理 |
|---|---|---|---|---|
| 根据精力曲线/截止日/优先级自动排任务 | 允许 | **可实现** | 精力曲线需用户手动配置或简单规则；无外部数据源 | 作为本地规则增强，基于已有 `propose_slots_for_draft` 扩展 |
| 会议过多时建议「拒绝/缩短/合并」 | 允许 | **可部分实现** | 只能给出建议，不能真的替用户回邮件/改他人日程 | 本地冲突分析面板新增建议卡片 |
| 专注时间保护、通知静音 | 不允许/无 API | **不可实现** | 宿主没有通知/勿扰/OS 级权限 | 明确说明依赖平台能力，比赛内不做 |
| 会议取消后自动释放时间块 | 允许 | **可实现** | 用户在本应用内取消事件后，可触发重新排程 | 删除/取消事件时调用现有自动排程逻辑 |
| 共享/团队/项目日历、权限分离 | 不允许 | **不可实现** | 无后端、无多用户、无共享存储 | 说明需平台级后端，比赛外规划 |
| 预约页面让别人选时间 | 不允许 | **不可实现** | 需要公网可访问的服务器与 URL | 比赛外规划 |
| 多人投票选时间（Doodle） | 不允许 | **不可实现** | 需要后端与实时同步 | 比赛外规划 |
| 实时共同编辑、评论、@提醒 | 不允许 | **不可实现** | 需要实时协作后端 | 比赛外规划 |
| 公开日历嵌入/订阅 URL | 不允许 | **不可实现** | 需要托管 ICS/CalDAV 服务 | 比赛外规划；当前可导出 ICS 让用户手动分享 |
| 收到机票邮件自动建行程 | 能力有但风险高 | **不建议做** | `mail` 能力仅限完整 Shell；自动读取邮件建日程越权且违反「数据不出设备」口径 | 比赛内不做；可演示手动粘贴 ICS/文本 |
| Slack mention deadline 自动提醒 | 不允许 | **不可实现** | Slack 域名不在白名单，无实时监听 | 比赛外规划 |
| Jira 状态变更同步日程 | 不允许 | **不可实现** | Jira API 不在白名单 | 比赛外规划 |
| Webhook/API/脚本可编程日历 | 不允许 | **不可实现** | 无接收 Webhook 的服务端，无脚本扩展点 | 比赛外规划 |
| 连接 Google/Outlook/Apple/飞书/钉钉/企业微信等 | 不允许 | **不可实现** | 需要 OAuth、多域名、账户体系 | 比赛外规划 |
| 插件市场 / mini-app 运行 | 不允许 | **不可实现** | Splash 无动态加载/插件模型 | 比赛外规划 |
| 每个日历独立 URL/API/嵌入代码 | 不允许 | **不可实现** | 需要后端服务 | 比赛外规划 |
| 本地搜索人/地点/标签/笔记/会议纪要 | 允许 | **可实现** | 附件、评论暂无数据模型；可搜索事件标题、地点、描述、笔记 | 新增本地搜索面板 |
| 自然语言统计查询（「上月开了多少会」） | 允许 | **可实现** | 依赖本地事件库；复杂查询可让 model 解析但需用户确认 | 新增统计面板，结果本地聚合 |
| 自动生成时间报告（会议成本/专注时长/加班趋势） | 允许 | **可近似实现** | 专注时长只能靠事件类型推断，无真实屏幕使用时间 | 基于事件时长与标签做近似报告 |
| 版本历史与回滚 | 允许 | **可部分实现** | 受 16 MiB 存储限制，只能保留有限快照 | 在现有「回滚上一次导入」基础上扩展事件级历史 |

## 复赛剩余时间内可落地子集

按「能在 10/13 23:59 前做完并通过全量回归」筛选，建议只做以下 4 项：

1. **本地时间搜索与统计查询**（不依赖 model 真机，纯本地实现）。
2. **近似的自动生成时间报告**（会议时长汇总、加班趋势、按标签统计）。
3. **事件级版本历史/回滚**（基于现有导入快照机制扩展）。
4. **会议取消后自动释放时间块**（复用已有排程函数）。

其余功能要么超出宿主权限，要么需要后端/第三方集成，不适合在复赛窗口内承诺。

## 不建议触碰的红线

- **自动读取邮件/Slack/Jira 并写入事件库**：即使技术可行，也会把用户数据送出设备，直接违反已写入 README/PRIVACY 的隐私口径，评委可据此扣分。
- **把 model 路径当作卖点**：当前 `card-host` 无法验证 `model.complete` 成功路径，任何依赖模型的功能都只能作为「可选增强」，不能放在核心卖点。

## 结论

用户提出的清单里，**约 70% 属于比赛外产品愿景**（多人协作、开放集成、自动化规则、插件生态），在当前 OctoSense 脚本宿主和比赛规则下无法落地。复赛收尾阶段应聚焦 **本地智能化**（搜索、统计、报告、历史回滚、自动重排），并把不能做的功能明确写进文档/答辩口径，而不是为了「看起来全」而写半套半成品。
