# ICS 导入 / 导出 · 功能设计

> OctoSense 日历 · 队伍 OMA · 2026-09-27
> 功能：把其他日历（Google Calendar / Apple 日历 / Outlook / 飞书）的日程同步进来，也能导出带走。

---

## 零、为什么这个功能比看上去重要

它不是一个"便利功能"，**它是整个演示闭环的地基**。

我前面在创新方案里说"外部事实来自邮件邀请"——但那条路是虚的：`personal-data` skill 读的是旧模块文件，README 自己标了 `not verified`。**我们其实没有任何一条可靠的"外部日程进入系统"的通路。**

ICS 导入补上了这个洞，而且补得很好：

| 特性 | 价值 |
| --- | --- |
| **真实** | ICS 是 RFC 5545 标准，不是我们编的 |
| **可演示** | 现场导出→导入→看到冲突，30 秒讲完 |
| **零 host 依赖** | 不需要 `mail` / `octos.*` / `matrix.*` 任何服务 |
| **数据可控** | 用户自己选哪份日历进来，正好对应授权模型 |
| **撞上主线** | 导入的外部事件**天然会跟私人预约冲突**——这就是选题场景 |

**一句话**：有了它，"会议改期撞上私人预约"这个场景才真的能跑起来，而且是用真实数据跑。

## 一、能力边界（先说清楚，这决定了架构）

我实测确认了脚本 API 的真实能力，有三个硬约束：

### ❌ 没有剪贴板 API

能力表里有 `clipboard` 这个 capability，但**脚本层没有读取接口**。文档原话：

> If something is not on this page, check the runtime source before using it.
> If it is not there either, **it does not exist for apps**.

所以"读剪贴板"这条路走不通。（我第一版判断错了，这里纠正。）

### ❌ 没有文件选择器

应用只能读自己的 jail（`<app-data>/<id>/`），**无法浏览用户文件系统**。

> ⚠️ 原文完全没有提及 file picker / document picker。
> 唯一能加载"用户提供的文件"的路径是相机捕获（落在 jail 的 `DCIM/`）。

所以"选一个 .ics 文件打开"这条路也走不通。

### ✅ 但 `TextInput` 能接收任意文本

**这是唯一可用的通路。** ICS 本质是纯文本，一份周的日程也就几 KB。所以：

> **导入方案 = 一个大文本框 + 粘贴 ICS 内容 + 解析入库**

这不是妥协，反而有个好处：**用户能看见自己粘了什么**，符合我们"授权可见"的产品哲学。

### ⚠️ 脚本语言很薄，解析器必须手写

**下面是逐条核对过源码的正确写法**（源码：`makepad/platform/script/src/string.rs`；
官方测试：`makepad/platform/script/test/src/main.rs` —— 测试文件比文档更权威）。

| 想做的事 | ✅ 正确写法 | ❌ 不存在的写法 |
| --- | --- | --- |
| 全局替换 | `s.replace(regex(p, "g"), r)` | ~~`regex(p,"g").replace_all(s, r)`~~ |
| 切分 | `s.split(regex(p, ""))` 或 `s.split("x")` | – |
| 取子串 | `s.to_chars()` → 数组，再拼 | ~~`s[0..3]` 切片~~ **没有切片** |
| 找子串 | `s.search(p)` → 索引或 `-1` | `s.contains(p)` |
| 前缀 / 后缀判定 | `s.strip_suffix(x) != s` / `search(p) == 0` | `s.starts_with(p)` / `ends_with(p)` |
| 正则捕获 | `s.match_str(re)` → `{value, index, captures}`；全局 regex 返回数组 | – |
| 大小写 | 用 `regex(p, "i")` 忽略大小写匹配 | `s.to_upper()` / `to_lower()` |
| 遍历 | `for i in n`（`0..n-1`）；`a..b` 范围 | `range(n)` |
| 集合操作 | `for` 手写；`retain(fn)`；`remove(i)` | `map` `filter` `join` `sort` `slice` `index_of` |

**两个会静默出错的坑**（Python 原型里专门做了断言）：

1. **`to_f64` 失败返回 `NaN`，不是 `nil`** —— 而 `NaN` 与任何值比较都是 `false`。
   所以判断解析是否成功**必须用正面守卫** `if v >= 0`，写 `if v != nil` 会永远进不去。
   （`SEQUENCE:3`、时分数值解析都会踩到）
2. **`replace()` 只替换第一处** —— 反折叠、四类转义还原**全都**是全局替换，
   漏一个 `"g"` 就会留下脏数据，而且不会报错，只是结果不对。

**单 handler 200000 指令 / 64 ms 是双限**，大 ICS 必须在**一个 handler 之外**分块续跑
（见 3.5 节），这是本项目最容易低估的一处工程约束。

**没有 ICS 解析库可用**，必须自己写。工作量真实存在，但完全可控（见第三节）。

## 三、ICS 解析器设计（核心工作量）

### 3.1 RFC 5545 的最小可用子集

完整 ICS 规范很大，但我们**只需要这些**：

| 字段 | 含义 | 必需 |
| --- | --- | --- |
| `BEGIN:VEVENT` / `END:VEVENT` | 事件块边界 | ✅ |
| `UID` | 唯一标识（用于去重、更新） | ✅ |
| `SUMMARY` | 标题 | ✅ |
| `DTSTART` | 开始时间 | ✅ |
| `DTEND` | 结束时间 | ✅ |
| `LOCATION` | 地点（**可行性检测要用**） | ⭐ 重要 |
| `DESCRIPTION` | 描述 | 可选 |
| `ORGANIZER` | 组织者（**改期建议要发给谁**） | ⭐ 重要 |
| `ATTENDEE` | 参与者 | 可选 |
| `STATUS` | CONFIRMED / TENTATIVE / CANCELLED | ⭐ 有用 |
| `SEQUENCE` | 版本号（改期会递增） | ⭐ 有用 |

**主动忽略**（不做，别浪费时间）：`RRULE` 重复规则、`VALARM` 提醒、`VTIMEZONE` 时区定义、附件、`RECURRENCE-ID`。

### 3.2 三个必须处理的坑

**坑 1：行折叠（Line Folding）**

ICS 规定单行超过 75 字节要折行，续行以**空格或 Tab 开头**：

```
DESCRIPTION:这是一段很长的描述，超
 过了七十五字节所以被折行了
```

**必须先反折叠**，否则解析全乱。这是最容易漏的一步。

**坑 2：转义字符**

值里的 `\,` `\;` `\n` `\\` 要反转义。注意 `replace()` 只替换第一处 → **必须用 `regex()` 做全局替换**。

**坑 3：时间格式有三种**

| 格式 | 类型 | 例子 | 处理 |
| --- | --- | --- | --- |
| `DTSTART:20261004T140000Z` | UTC | 带 `Z` 结尾 | 转本地 |
| `DTSTART;TZID=Asia/Shanghai:20261004T140000` | 本地时区 | 带参数 | 按 TZID |
| `DTSTART;VALUE=DATE:20261004` | 纯日期 | 全天事件 | 标为全天 |

参数在 `;` 后面。**分隔符取第一个 `:`，不是最后一个**（这里我第一版想错了，已纠正）：
RFC 5545 规定 key 区（含参数）**不含裸冒号**，冒号在 key 区里必须写成 `\;` 转义之外的
形式——实际上参数值里的冒号是允许的（如 `TZID` 一般不含，但 `ALTREP="..."` 里可能有），
不过**第一个未经引号包裹的 `:` 就是 key/value 分界**，这是规范行为。
保险起见：从开头扫描，遇到第一个 `:` 就切。
（值里含 `:` 完全正常——URL、时间都在值里，所以**绝不能从右往回找**，
那样会把 `https://...` 的冒号误当分隔符。）

### 3.3 解析流程（用 `for` 循环手写）

```
1. 规范化换行：把 \r\n 和 \r 统一成 \n
2. 反折叠：把 "\n " 和 "\n\t" 换成 ""
3. split("\n") 切成行数组
4. for 每行：
     - search(":") 找第一个冒号 → 左边是 key 区，右边是 value
     - key 区可能含 ";参数"，split(";") 拆开
     - 遇 BEGIN:VEVENT → 开始收集
     - 遇 END:VEVENT → 把收集到的事件 push 进数组
     - 其他 key 按表存进当前事件
5. 返回事件数组
```

**关键点**：步骤 2 的反折叠必须在 split **之前**做，否则折行会变成独立行。

### 3.4 日期解析（无 `range()`，用纯算术）

```
"20261004T140000Z"
   ↓ 检查末尾是 Z
   ↓ 取前 8 位 = 20261004
   ↓ 第 9 位是 T
   ↓ 后 6 位 = 140000
   ↓ 切成 y/m/d/h/min/s，用 "" + 数字 做字符串截取
   ↓ to_f64() 转数字（注意：失败给 NaN，用 if v >= 0 守卫）
```

⚠️ `to_f64()` 对非数字返回 **NaN 不是 nil**，且 **NaN 与任何值比较都是 false**，所以一律用 `if v >= 0` 守卫。

## 四、去重与合并（这是"同步"的真正含义）

用户说"可以直接同步过来"——**同步的关键是幂等**，重复导入不能产生重复事件。

### 去重键

`UID` 是 ICS 规范里唯一的身份标识。**用 UID 做主键**：

| 情况 | 处理 |
| --- | --- |
| UID 不存在 | **新增** |
| UID 存在，`SEQUENCE` 更大 | **更新**（对方改期了！） |
| UID 存在，`SEQUENCE` 相同且内容相同 | **跳过**（幂等） |
| UID 存在，`SEQUENCE` 更小 | **忽略**（本地更新） |

`SEQUENCE` 递增正是**改期**的语义——**这直接喂给我们的"差分扫描"引擎**：导入时发现某个 UID 的 SEQUENCE 变大，就是"外部发生了变更"，这正是要触发冲突检测的信号。

### 合并策略（导入时让用户选）

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| **合并**（默认） | 按 UID 增量更新，保留本地事件 | 日常同步 |
| **替换** | 清空同名来源的事件再导入 | 重新拉一份干净的 |

### 来源标记（对应授权模型）

每个导入的事件打上**来源标签**：
- `source: "ics:google"` / `"ics:outlook"` / `"ics:local"`

这个标记有两个用处：
1. **UI 上标注来源** —— no-facts 规则要求"事实来源必须注明"
2. **授权边界** —— 导入的事件默认是 `negotiable`，本地手动建的可标 `non_negotiable`

## 五、导出设计

导出比导入简单，**方向反过来**：

```
事件数组 → for 循环拼字符串 → 写进 jail → 显示在文本区供复制
```

**同样受限于"没有剪贴板写接口"**，所以要：
1. 生成 ICS 文本
2. `fs.write("export/calendar.ics", text)` 存进 jail
3. **显示在一个只读大文本框里**，用户自己选中复制

⚠️ 导出必须包成合法 ICS：
- 首行 `BEGIN:VCALENDAR` + `VERSION:2.0` + `PRODID`
- 每个事件 `BEGIN:VEVENT` … `END:VEVENT`
- 尾行 `END:VCALENDAR`
- **折行**：超过 75 字节要主动折（跟导入的反折叠是对称的）
- 转义：标题里的 `,` `;` 要转义

**导出是"带走你的数据"的权利**，这在答辩里是个好点：**我们没有锁定用户**。

### 解析预览（**关键的一步**）

点"解析预览"后，**先不写库**，而是显示：

```
检出 12 个事件：
  ✅ 9 个新增
  🔄 2 个更新（SEQUENCE 变化 → 可能已改期）
  ⏭ 1 个已存在，跳过
  ⚠️ 1 个解析失败（第 47 行，缺 DTEND）
```

**为什么要预览**：这是"**先展示、后执行**"的哲学——**跟我们的授权模型是同一套价值观**。Agent 不偷偷改你的日历，先给你看清楚要发生什么。

**预览里最该突出的是"🔄 更新"那 2 个** —— 因为那就是**改期**，就是要触发冲突检测的事件。

## 七、与创新主线的接口（这才是重点）

ICS 导入不是孤立功能，**它是三处创新的数据入口**：

| 创新点 | ICS 怎么喂它 |
| --- | --- |
| **创新 2 · 状态机** | `STATUS:CONFIRMED` → `confirmed`；`TENTATIVE` → `proposed`；导入后本地发起的改期 → `awaiting_reply` |
| **创新 3 · 可行性** | `LOCATION` 字段是可行性检测的输入——"两场会在不同地点"就是隐性冲突的判据 |
| **创新 4 · 承诺重量** | 本地手建的事件 → `non_negotiable`；导入的外部事件 → `negotiable`（**别人排的会本来就可以谈**） |
| **差分扫描（主动守护）** | 反复导入同一份 ICS，`SEQUENCE` 变大的那些就是"外部变了"，正是主动提醒的触发信号 |

**最后一行的意思是**：用户不需要我们真的去连 Google 的服务器。**用户自己重新粘一次 ICS，就完成了"同步"**——而这次粘的动作，恰好就是我们的触发时机。

> 这是个很妙的架构：**我们把"没有后台推送"这个限制，转化成了"用户主动同步时才扫描"的合理设计。** 每一次导入就是一次差分扫描。

## 九、建议的实施顺序

1. **先写纯解析函数**（不碰 UI）：喂一段硬编码 ICS 字符串，`fs.write` 输出解析结果 → 验证逻辑
2. **再接 UI**：TextInput → 解析预览 → 确认导入
3. **再做导出**：反向拼接 → 写 jail → 只读展示
4. **最后接主线**：把导入结果喂给冲突检测 + 差分扫描

**第 1 步是关键**：解析逻辑对了，整个功能就成了一半。而且它**可以脱离图形环境测试**，在 Windows 工具链还没跑通时就能先做起来。
