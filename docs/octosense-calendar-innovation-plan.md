# OctoSense 日历 · 创新方案

> 队伍 OMA · Agentic App 黑客松 2026 · 2026-09-27 初稿
> 目标：回答一个问题 —— **相比传统日历，我们能在哪里做出真正的创新？**

---

## 零、先说结论

**传统日历是一个「记录工具」，我们要做的是一个「承诺管理器」。**

传统日历的核心假设是：**时间是由人主动填进去的空格子**。你打开它，看格子，想，然后自己决定。它记性好、绝不越权、也绝不帮忙。

它的三个致命缺口：

| 缺口 | 传统日历的表现 |
| --- | --- |
| **它知道冲突，但不管冲突** | 画一条红线说「重叠了」，然后呢？没有下文。解决冲突的成本 100% 落在人身上 |
| **它只知道「我有空」，不知道「我能不能」** | 14:00 是空的，但你上一场会在城东、下一场在城西；它不认为这是冲突 |
| **它不区分「承诺」的重量** | 私人看诊和团队例会，在格子里长得一模一样。但一个是可协商的，一个不是 |

所以我们的创新不应该是「更好的日历 UI」——那是 1% 的改进。**应该是把日历从「显示层」下沉成「决策层」**：日历不再是你要看的东西，而是替你把话想好了、直接问你要不要的东西。

一句话定位：

> **传统日历告诉你「什么时候是你的事」。我们告诉你「接下来该做什么，以及为什么」——并且在动你任何一个承诺之前，先来问你。**

## 一、这个生态给了什么（决定了创新点能落在哪）

读完 `OctoSense-App-Hub` 与整个 OctoSense-org 之后，几个**结构性事实**必须说清楚，因为它们既是最好的机会，也是最硬的约束：

### 1.1 官方系统应用里**没有日历**

`OctoSense-System-Apps` 的 6 个第一方应用是：News、Photos、Maps、Camera、Mail、AI providers。

**日历是空的。** 这不是巧合——官网 12 篇应用体验指南把它列为场景之一，而系统应用层没做。我们不是在给一个成熟产品加功能，**我们是在填一个官方留白的生态位**。这个叙事在答辩时极有价值。

### 1.2 日历数据在系统里"存在但不完整"——这是最大机会也是最大陷阱

关键发现：

- AppCard 的 `personal-data/` 是一个 **octos skill，对 Mail / Calendar 做只读搜索**
- 但它读的是**旧原生 Mail 模块**留下的文件，README 自己标注 **"not verified"**

**结论**：日历的"上游事实源"目前是**松的**。这直接撞上赛事的 **no-facts 铁律**——「不得编造状态、操作成功或执行结果」。

所以我们必须做两件事：
1. **自己负责日历事件的权威存储**（`storage` 能力内的一个结构化事件库），不假装能从某个不存在的系统日历里读
2. **对外部事实（邮件邀请、消息、天气、路程）走 host service 或明确声明的 hosts**，并在 UI 上**逐条标注来源**

> 这一条会决定我们能不能通过复赛的"结果核验"。做对了是加分项（诚信 + 工程严谨），做错了是直接出局。

### 1.3 真正的能力边界（写代码前必须记牢）

| 事实 | 含义 |
| --- | --- |
| 商店应用**不能携带原生代码** | 没有 Rust/JNI。只能 `page.card`（纯展示、无逻辑）或 `main.splash`（有状态/处理函数/请求） |
| 所以日历**必须是脚本应用**（`main.splash`） | 卡片应用没有逻辑，扛不住状态机 |
| **没有本地通知/后台定时唤醒能力** | 能力清单里没有 `notify`。**"主动守护"只能发生在 App 被打开或被打断时**，不能真后台跑 |
| `octos.turn.start` 可以让宿主助手替应用干活 | 但**只有 `os.` 系统应用能拿到 `llm`**；`octos.*` 服务是否对商店应用开放，**必须实测** |
| `matrix.*` 有 45 个具名能力 | 可直接读房间消息/Rinx 会话，是"邀请来自消息"这条链路的现成通路 |
| 敏感信息**绝不能在应用内收集** | 密码/PIN/OAuth 只能在 host 的 **sheet** 上输入。应用拿不到凭据，只拿到结果 |

**"确定性自动化"必须在这个天花板之下设计。** 我们原以为可以做的"后台守护"，实际只能做成"每次打开/被唤醒时的时间差分扫描"。这反而逼出一个更诚实、也更好演示的设计（见第三节）。

### 1.4 脚本语言的实际能力（实测，2026-09-27）

⚠️ **重要：脚本环境比预想的薄，写代码前必看。**

| 项目 | 实情 |
| --- | --- |
| **剪贴板** | ❌ **能力表有 `clipboard`，但脚本层没有读取接口**。文档原话：不在文档上的，查运行时源码；再不在这就不存在 |
| **文件选择器** | ❌ 不存在。应用只能读自己的 jail（`<app-data>/<id>/`），**无法浏览用户文件系统** |
| **文本输入** | ✅ `TextInput` 能接收任意文本（`on_change: \|text\|` / `on_return: \|text\|`）。**必须给数值型 `height`** |
| **文件存储** | ✅ `fs.read/write/append/exists/list/mkdir/remove`。无 rename/stat/二进制写。**单文件 1 MiB**，jail 上限 16 MiB（商店应用） |
| **网络** | ✅ `net.http_request`，只能到 `network.hosts` 里声明的 hosts。无 `net` 时 `net` 变量根本不存在 |
| 数组方法 | ⚠️ **只有** `push pop clear len remove(i) retain(fn)`。**没有** `map filter join sort slice` |
| 字符串方法 | ⚠️ **只有** `len trim split search replace strip_prefix strip_suffix url_encode url_decode to_f64 match_str match_all`。**没有** `contains to_lower to_upper starts_with ends_with` |
| `replace()` | ⚠️ **只替换第一处**！全局替换必须用 `regex(pattern, "g")` |
| 循环 | `for i in n` / `for v in array` / `for i v in array` / `for k v in object`。**没有 `range()`** |
| 正则 | ✅ `regex(pattern, flags).test(s)` / `.exec(s)` |
| JSON | ✅ `s.parse_json()` / `v.to_json()`。但**无效 JSON 不保证返回 nil**，要检查字段 |
| `to_f64()` | ⚠️ 非数字返回 **NaN 不是 nil**，且 NaN 与任何值比较都是 false → **一律用 `if v >= 0` 守卫** |
| `host.request` | ✅ `host.request(svc, args, fn(r))`，`r.is_ok` / `r.data` / `r.error`。也有 `host.capabilities()` / `host.has()`。**没有 `host.prompt`** |

**结论：没有第三方库可用，所有解析逻辑必须手写。** ICS 导入功能已按此约束设计完成 —— 见 [`ics-import-export-design.md`](ics-import-export-design.md)。

## 二、创新点：五条创新线

### 创新 1 ★★★ 授权粒度（最可能被评审记住的一条）

官方体验指南第 06 段已经把话说透了：

> 「发送改期建议」与「修改私人安排」是**两项独立授权**

**但今天没有任何日历实现这个区分。** Google Calendar 只有一个「允许修改事件」的粗粒度开关。这是一个被官方点名、却无人实现的真空。

我们的设计——**三分量授权模型**：

| 授权 | 语义 | 默认 |
| --- | --- | --- |
| `observe` | 读我的日程、检测冲突、**生成**提案 | 开 |
| `propose_outward` | 把我起草的改期建议**发给外部**（邮件/消息） | **关**，逐次确认 |
| `mutate_own` | 改动**我自己的**私人安排 | **关**，逐次确认 |
| `share_availability` | 对**共享日历成员**只暴露"该时段不可用"，**不暴露原因** | 开 |

三条独立、每次动作都分别检查。这不只是"权限设置"——它是**产品哲学的外化**：Agent 可以替你想、不能替你答应。

**第四分量 `share_availability` 是隐私的关键**（思路来自豆包方案的"共享日历空间 + 可隐藏私人日程"）：

现实里有**三方**，不是两方——
- **我**（私人日历持有者）
- **会议组织者**（发来改期邀请的人）
- **共享日历的其他成员**（家人 / 同事）

对组织者：可以发"我建议改到 14:15"。
对共享成员：只能说"14:00 这一格不可用"——**不能说"因为要看病"**。

> `"私人预约"` 这四个字本身，就已经泄露了隐私。所以**"不可用"必须是一个不带原因的谓词**，而不是一句打了码的描述。

这让隐私设计从"合规模板"变成了**有真实颗粒度的设计**。答辩时这是能讲出细节的点。

**这正对应赛事的第一评审权重（Agent 自动化），也是"Human in the loop"的工程化落地。** 答辩时可以直接说：我们把官网指南里的一句话，变成了一个可验证的授权状态机。

### 创新 2 ★★★ "尚未确认"是一等公民状态

官方指南第 02 段第 4 步：「**明确什么尚未确认**」。

传统日历的数据模型只有"有/无"——事件要么在，要么不在。**没有"我提议了但对方还没回"这个状态**，所以人只能靠脑子记。

我们给每个事件一个显式的状态机：

```
proposed ──→ awaiting_reply ──→ confirmed
    │              │
    └──────────────┴──→ contested / declined / expired

inferred ──→ confirmed        （推断 → 核实：如"调休预判"到官方发布）
```

界面上**永不混同**：
- `confirmed` 实心、正常字重
- `awaiting_reply` 半透明 + 虚线边框 + 「已发出，等 David 回复」
- `proposed`（我还没发）斜体 + 「未发送」
- `inferred` 点线边框 + 「预判，待核实」

**为什么这条重要**：它是 no-facts 规则在 UI 层面的直接体现——**绝不把"我打算做"画成"已经做"**。评审看截图就能看出我们懂规则。

**加上 `inferred` 状态之后，这条创新变得更强**：它把"事实"分成了三层（权威 / 待确认 / 推断），而 **no-facts 规则的本意不是"不许推断"，而是"不许把推断伪装成事实"**。只要状态可见，推断就是合法且有价值的。

> 这个想法来自豆包方案里的「调休预判」功能（官方没发通知也给预判版，发布后一键修正）。
> 我们把它**从"一个功能"升格为"状态机里的一个状态"**——同一个思路，但成了体系的一部分。

**UI 视觉编码（吸收豆包的日期分级思路）**：

| 视觉元素 | 编码含义 |
| --- | --- |
| 竖条颜色 | **承诺重量**：红=不可协商 / 黄=可协商 / 灰=灵活 |
| 边框样式 | **确认状态**：实线=已确认 / 虚线=待回复 / 点线=推断 / 斜体=未发送 |

一眼就能看出「这个不能动」和「这个还没定」，也让 Agent 的提案**显得有依据而不是瞎猜**。

### 创新 3 ★★★ 可行性 ≠ 空闲（"隐性冲突"检测）

这是我认为**最有技术含量、也最容易被忽视**的一条。

传统日历找冲突的方式是「两个时间块重叠了」。这个判断弱得可怜。真实的冲突长这样：

> 会议改到 **14:00**、地点换到**另一栋楼**。
> 日历说：14:00 是空的，没冲突 ✅
> 现实是：你 13:30 在城东开会，14:00 要出现在城西。**你到不了。**

所以要引入 **`feasibility`（可行性）** 这个比 `availability`（空闲度）高一级的概念。它需要把**外部事实**拉进来算：

| 维度 | 需要的数据 | 数据来源（必须标注） |
| --- | --- | --- |
| 路程时间 | 两地通勤耗时 | `os.maps` / 声明 hosts（如公开路径服务） |
| 出发时刻 | 结合天气的预留量 | 天气 host |
| 精力/时序 | 是否连续开会、是否跨午休 | 本地事件库 |
| 无准备时间 | 两个会议背靠背、零缓冲 | 本地事件库 |

产出一个**"够不够"的判定**，而不是一个"空不空"的判定：

```
14:00 会议（另一栋楼）
  ⚠️ 不可行：需 35 分钟路程，你有 30 分钟。缺 5 分钟。
  → 建议：会议推迟到 14:15，或上一场提前 10 分钟结束
```

**这是传统日历在架构上做不到的事**——因为它没有"外部事实"这一层，也没有 agent 去把事实拉进来算。这就是 Agentic 与非 Agentic 的分水岭。

### 创新 4 ★★ 冲突的"重量"与代偿解，而不是二选一

传统日历遇到冲突只会让你选 A 或 B。但真实世界里有大量**局部解**：

| 冲突 | 传统日历给的 | 我们给的 |
| --- | --- | --- |
| 例会 vs 私人看诊 | 「重叠了」 | **看诊不可动**（不可协商承诺），提议例会改期 |
| 两场会都重要 | 让你选 | 「各缩 15 分钟 + 换到有设备的小会议室」——**保住两场** |
| 出行冲突 | 不管 | 「提前 10 分钟结束上一场」或「改线上」 |

关键是**给承诺分级**：
- `non_negotiable`（不可协商）—— 私人医疗、孩子接送、法定事务。Agent **永不提议改动**
- `negotiable` —— 团队例会、内部同步。可提议
- `flexible` —— 单人会、缓冲段。可自动调整

**这条的价值**：它把"冲突"从一个**问题**变成了一个**待求解的约束满足问题（CSP）**。传统日历只做约束**检测**，我们做约束**求解**。这是本质差异。

### 创新 4.5 ★ 周末之外的"时间地貌"：为什么总是排不下

> 这一条是被豆包的「时间能耗分析报表」触发的——**它统计"时间花在哪"，我们追问"为什么排不下"**。

上面四条都在解决**单次冲突**。但真实生活里更痛的是**结构性冲突**：不是这一次排不下，而是**每周都排不下**。

传统日历永远不会告诉你这件事，因为它只看单个时间块。**但只要把事件库做纵向聚合，就能看出"地貌"**：

| 诊断 | 判据 | 输出 |
| --- | --- | --- |
| **连续性饥饿** | 连续 N 周无 ≥2h 的完整空闲段 | 「你已经 3 周没有超过 2 小时的完整时间块了」 |
| **会议密度中毒** | 每周会议时长占比 > X% | 「本周 71% 工作时间在会议里，仅 4 小时可用来做事」 |
| **缓冲清零** | 背靠背会议占比 > Y% | 「你今天 5 场会零缓冲，任一超时都会连锁」 |
| **边界侵蚀** | 出现早于 9:00 / 晚于 19:00 的日程频率上升 | 「本月早间日程比上月多 6 次」 |

**为什么这属于 Agentic 而不是统计**：报表是**事后**的（豆包路线），地貌是**事前**的——它的作用是**影响下一次排期的决策**。

> 当组织者提议"周四 16:00 开会"，Agent 不只知道那时段空着，还知道**你本周缓冲已经清零了**，于是它会说：
> 「周四 16:00 可行，但你本周已有 5 场背靠背会议。建议改到周五上午——那是你本周唯一的完整时间块。」

**这是"可行性"的第三层**：不是"来不来得及"（创新 3），也不是"该不该动"（创新 4），而是"**这样排下去会发生什么**"。

而且它成本很低——**纯本地事件库聚合，不依赖任何外部事实**，在能力受限的环境里是最稳的创新点。作为创新 3 的补充（外部事实）形成"内外双算"。

### 创新 5 ★★ 反哺 OctoSense 生态（拿"技术突破奖"的路线）

赛事评审的第二权重是"项目反哺与 ROM 技术突破"，且有硬要求：**必须可复用、可验证、给出补丁与前后对比**。

我们天然可以交出这些：

| 可交付 | 形式 | 为什么别人需要 |
| --- | --- | --- |
| **`calendar` host service** | Rust，仿照 `apps/mail/host-service` 的结构 | 系统应用层没有日历。这是我们填的空白 |
| **日历事件 + 授权状态机的 skill 规范** | `a2app/` 风格的 requirements-only spec + lint 规则 | 其他应用需要读写日程时可直接复用 |
| **`feasibility` 判定协议** | 一份能力/接口约定文档 | 任何"时间敏感"应用（出行、快递、票务）都用得上 |
| **L0 卡片模板** | 冲突卡片、改期提案卡片 | 设计流程可直接调用 |

**注意取舍**：反哺是加分项，**必须先有能跑的 Agentic 应用**。低层改动本身不构成突破。所以顺序是：底座先跑通 → 再抽出可复用件。

## 三、"主动守护"的具体设计（在能力天花板之下）

这是最需要动脑子的地方。**没有后台定时器**，所以"主动"必须重新定义。

### 3.1 触发模型：差分扫描（Delta Scan）

App 被打开 / 被 `octos.turn.start` 唤醒时，执行一次**状态差分**：

```
拉取外部事实（邮件邀请 / 消息 / 天气 / 路程）
    ↓
与本地事件库对账（reconcile）
    ↓
比上一次快照（snapshot）→ 只算「变了什么」
    ↓
差分命中规则 → 生成卡片 / 提案
```

**只有差分才推消息。** 这避免了"每次打开都刷一堆通知"的骚扰，也正好对应官方指南第 07 段：

> 「邀请、日程变更、准备时刻分别触发；**多次通知持续更新同一个事件**」

我们把它实现为**同一事件上的状态演进**，而不是三条独立通知。这在 UI 上会非常好看：一张卡片从「检测到冲突」→「已生成提案」→「已发出，等待回复」原地演进。

### 3.2 对外动作走 host，凭据不进应用

发改期建议 = 发邮件/发消息。按生态规则：

- 应用调用 `host.request("mail.send", …)` 或 `matrix.send_message`
- 需要登录时，**host 在自己的 sheet 上收凭据**，应用只拿到"成功/失败"
- 应用**永远不持有 token、密码、socket**

这是硬约束，也是我们在答辩里能讲的"安全设计"。

### 3.3 诚实兜底

如果 `octos.*` 助手服务实际对商店应用不开放（**待实测**），降级方案：
- 走 `matrix.*` 的读写能力做"消息侧"链路
- 走声明 hosts 拉天气/路程
- 用纯脚本状态机做冲突求解（不依赖 LLM）

**无论哪条路，应用都是可运行、可演示的。** 不把成败押在未验证的接口上。

## 四、跟传统日历的逐条对照

| 维度 | 传统日历 | 加功能型日历（豆包路线） | OctoSense 日历（我们的） |
| --- | --- | --- | --- |
| **谁做决定** | 你 | **你**（只是工具更强） | **你想、你点头**（Agent 想在前） |
| 用户角色 | 操作者 | 操作者（+ 更多功能） | 审阅者 |
| 冲突处理 | **检测**（画红线） | 检测（+ 更醒目） | **求解 + 代偿**（给方案） |
| 冲突判据 | 时间块重叠 | 时间块重叠 | **可行性**：路程、缓冲、精力、时序 |
| 时间视角 | 单次 | 统计报表（**事后**） | **地貌 + 事前**（影响下次排期） |
| 承诺权重 | 全部等价 | 四级标记（可视） | 三级重量 + **决策含义**（Agent 据此行动） |
| 「待确认」 | 不存在 | 不存在 | **一等公民状态**（含 `inferred` 推断态） |
| 授权 | 一个「允许修改」开关 | 共享空间权限 | **四分量独立授权** + 隐私颗粒度 |
| 主动性 | 被动 | 提醒（**能力上做不到**） | **差分扫描**（能力内可行） |
| 事实来源 | 你手输 | 平台内容 | 权威/待确认/推断**三层标注** |
| 形态 | 独立 App | 独立 App | **卡片 + 应用双落位** |
| 数据边界 | 同一 App | 同一 App | **隔离区 + 能力门禁** |

### 三层递进（答辩可用的叙事）

> 1. **普通日历**：日期展示 —— 你记，它存
> 2. **加功能型日历**（豆包路线）：提醒 + 统计 + 报表 —— **工具更强了，但决定还是你做**
> 3. **我们**：Agent 替你想清楚，决定权在你手上 —— **换了一层**

**差异不在功能多少，而在"谁在做决定"。**

## 五之二、与豆包版方案《创新型日历软件产品设计方案》的对照

> 来源：`feishu.doubao.com/docx/TY64dELF1oyJgWxBwBZcjHQUnu5`（2026-09-27 抓取全文）
> 该文档由豆包 AI 生成（文内 `is_ai_gen: true`），共 33 段，结构为：整体定位 / 开发落地思路 / 基础必备功能 / **十大独家创新核心功能** / 核心亮点总结

### 它的十大"独家创新"逐条

| # | 豆包的创新 | 我们的评价 |
| --- | --- | --- |
| 1 | **时间能耗分析报表** —— 按工作/学习/休息/娱乐/社交五维统计，可视化饼图折线，识别"无效耗时" | ✅ **可借鉴**：这是"时间去哪了"的反思层，我们没做。但要注意它是**统计**不是**决策** |
| 2 | **动态调休智能预判** —— 提前预判年度调休，官方发布后一键修正 | 🔥 **最值得借鉴的一条**，理由见下 |
| 3 | **场景化日程模板一键套用** —— 上百种模板（备考、通勤、健身） | ⚠️ 内容运营活，对黑客松性价比低 |
| 4 | **日期记忆回溯** —— 回溯任意日期，调取当年天气/节日/日程，做"时光日记" | ⚠️ 情绪价值功能，非遗珠。跟"会议改期"选题关联弱 |
| 5 | **适配作息智能提醒** —— 熬夜提醒、久坐提醒、柔性引导 | ❌ **踩坑**：我们能拿到的能力里**没有后台通知**，做不了 |
| 6 | **多人日程协同共享空间** —— 家庭/同事/好友三类共享空间，权限分级 | ✅ **可借鉴**：与我们的授权模型天然互补 |
| 7 | **节气民俗 + 生活指南联动** | ❌ 内容功能，非技术差异 |
| 8 | **专注计时 + 日程绑定** —— 锁手机、统计专注时长 | ❌ **踩坑**：锁定其他应用属系统级能力，商店应用拿不到 |
| 9 | **重要日期智能分级标记** —— 紧急/重要/常规/纪念四级 + 超期自动归类复盘 | 🔥 **最值得借鉴的第二条**，理由见下 |
| 10 | **无仪式感极简年度时间总结** —— 年末生成纯干货时间年报 | ⚠️ 好产品感，但演示时机不对（年末功能） |

### 三条真正该偷师的

#### 偷师 1：调休预判 —— "官方未发布的事实，可以先给一个明确标注的预判"

这是豆包全篇最聪明的一条，而且**它直接解决我们的一个真实困境**。

我们的 no-facts 约束让我们很保守：只敢展示"已确认"的事实。但豆包的思路是：

> 官方还没发通知，**照样可以先给预判版**，等官方发布后**一键自动修正**。

它把"事实"分成了两层：**权威事实**（官方通知）和**推断事实**（基于历年规律）。只要**标注清楚是哪一层**，推断就是合法的、有价值的。

**这可以直接嫁接到我们的可行性检测上：**

| 事实类型 | 例子 | 展示方式 |
| --- | --- | --- |
| 权威事实 | 邮件邀请原文、官方放假通知 | 实心，标注来源 |
| **推断事实** | 路程耗时（基于经验值）、调休预判 | **虚线 + "预判，待核实"** |

**这恰好和我们的创新 2（"尚未确认"状态机）是同构的！** 调休预判 = 一个 `inferred` 状态；官方发布 = 迁移到 `confirmed`，"一键修正" = 状态迁移动作。

**结论：把豆包的"预判 + 修正"吸收成我们状态机里的一个状态。** 一举两得——既有了它的亮点，又强化了我们自己的理论一致性。

#### 偷师 2：日期分级 → 我们的"承诺重量"需要一个可视化层

豆包的"紧急/重要/常规/纪念"四级标记，以及**"临近到期自动升级提醒权重"**这个细节——这个"权重动态变化"的想法很好。

我们的创新 4 已经有了 `non_negotiable / negotiable / flexible` 三级**承诺重量**，但那是**数据层**的。豆包提醒我们：**它需要在 UI 上可见**，否则用户不知道 Agent 的决策依据是什么。

**吸收方案**：给事件加一个视觉编码——
- 竖条颜色 = 承诺重量（不可协商红 / 可协商黄 / 灵活灰）
- 边框样式 = 确认状态（实线已确认 / 虚线待回复 / 点线推断）

这样**一眼就能看出"这个不能动"**，也让 Agent 的提案显得有依据而不是瞎猜。

#### 偷师 3：共享空间 → 我们的授权模型天然支持多方

豆包的"家庭/同事/好友三类共享空间 + 权限分级 + 可隐藏私人日程"，其实**正是我们这个选题的核心场景**：

> 会议改期撞上私人预约 —— "私人预约"就是别人看不到的那部分。

我们原方案只讲了"我 vs 外部邀请人"两方。豆包提醒我们其实有**三方**：
- **我**（私人日历持有者）
- **会议组织者**（发来改期邀请的人）
- **共享日历的其他成员**（家人/同事）

**吸收方案**：授权模型的 `propose_outward` 应该细化——你可以把改期建议发给组织者，但对**共享日历成员**只能显示"该时段不可用"，**不泄露原因**（"私人预约"这四个字本身可能就泄露隐私）。

这一条让我们的隐私设计从"合规模板"变成了**有真实颗粒度的设计**，答辩时会加分。

### 一条必须躲开的坑

**豆包的方案有一个致命问题：它把 Agentic 做成了"功能清单"。**

十大创新里，有 **6 条是传统 App 就能做的功能**（模板库、节气内容、年报、回溯、分级标记、报表）——它们是**好产品功能，但不是 Agentic 能力**。而且其中至少 **2 条（后台提醒、锁定手机）在我们能拿到的能力里根本做不到**。

问题在于**赛事的评审权重**：

> **先看 Agent 自动化能力**，再看反哺与技术突破。

豆包这份方案如果直接交上去，评委看到的会是一份**功能规划书**，而不是一个**Agentic 应用**。它的"主动"只停留在第 5 条（智能提醒），而那条恰恰实现不了。

**我们的路线必须坚持**：Agent 自己盯状态 → 自己算 → 自己起草 → 等你点头。**差异不在功能多少，而在"谁在做决定"。**

### 一个可以直接用的产品叙事

豆包那份文档里有一句话写得很好，值得直接引用：

> **"区别于传统日历只做「日期展示」，实现「被动记录时间→主动管理时间→优化生活节奏」的升级。"**

这句话的**方向**和我们完全一致（被动→主动），只是豆包走的是"提醒/统计"路线，我们走的是"决策/授权"路线。

**答辩时可以做这个对比**：
- 普通日历：日期展示
- 加功能型日历（豆包路线）：提醒 + 统计 + 报表 —— **工具更强了，但还是你自己做决定**
- **我们：Agent 替你想清楚，但决定权在你手上** —— **换了一层**

这个三层递进的叙事，比单纯说"我们比传统日历好"有力得多。
